# 完成した曲から「アコギだけ」を取り出す：既存モデルの組み合わせ方を実験で詰めたら SDR が 3.1 → 7.6 dB になった話

ミックス済みのステレオ曲から、アコースティックギターの音だけを取り出すツールを作りました。新しい分離モデルを一から学習したのではありません。公開済みの音源分離モデルを**どう組み合わせ、どう動かすか**を、正解付きのデータで1つずつ検証しました。

結果は、検証セットの平均 SDR で次のとおりです。

- 公開モデル単体のベスト：**3.13 dB**
- 最終的なパイプライン：**7.62 dB**

この記事では、何を試し、何が効いて何が効かなかったかを順番に紹介します。

> **この記事で分かること**
> - 「アコギだけ」の分離がなぜ難しいのか
> - 正解のない曲を相手に、何を物差しにモデルを選んだか
> - 効いた手（アンサンブル、推論チャンク長、小さな後段ネットワーク）と効かなかった手
> - CPU 4コアだけの環境で 45 回の実験を回すための工夫と、ハマったところ

---

## 1. やりたかったこと

対象は YouTube で公開されている1曲（ko-ko-ya「Frevo!」、2分12秒）です。アコースティックギターに加えて、バイオリンやクラリネットなどが同時に鳴っています。

出力は次の2本です。

- `acoustic_guitar.wav`：アコギだけ
- `non_acoustic_guitar.wav`：それ以外（元の曲 − アコギ。足すと元の曲にぴったり戻る）

優先順位は最初に決めておきました。

1. **他の楽器が混ざらないこと**（漏れが少ない）
2. **そのうえで、ギターの音をできるだけ削らないこと**

この2つはトレードオフです。「怪しい音は全部消す」ようにすれば漏れは減りますが、ギターも痩せてしまいます。

### なぜ難しいのか

- 一般的な分離モデルが出す「ギター」は、エレキとアコギを区別しないことが多いです。
- アコギの音域は、バイオリン、マンドリン、ピアノ、エレキのクリーントーンなどと重なります。
- 対象曲の音源は AAC 圧縮で、16 kHz より上がもともとカットされています。

## 2. まず物差しを作る：正解付きの検証セット

対象曲には「正解のアコギ音源」がありません。耳だけでモデルを選ぶと、どうしても主観がぶれます。そこで、**正解が分かっている検証セット**を先に作りました。

| 種類 | クリップ数 | 中身 |
|---|---|---|
| 実録音のマルチトラック | 19 | 楽器ごとに録られた実際の曲から、アコギと残りをミックスし直したもの |
| 合成シナリオ | 22 | アコギ単体の録音に、狙った「邪魔者」を重ねたもの |

各クリップは 12 秒で、合計 41 クリップです。合成シナリオは、苦手になりそうな状況を狙って作りました。たとえば次のようなものです。

- `buried`：ギターが他の楽器より 12 dB 以上小さい
- `clean_electric`：アコギと似た音色のエレキ
- `strings` / `winds`：弦楽器・管楽器との重なり
- `plucked`：マンドリンやバンジョー
- `chamber_frevo`：対象曲に近い、ギター＋バイオリン＋クラリネットの編成

素材には GuitarSet、Mixing Secrets（RawStems）、URMP、GAPS、GuitarJam を使いました。学習用と検証用で**曲が重ならないように**分けています。ライセンスは素材ごとに異なり、非商用の研究用途に限られるものも含まれます。そのため音声データはリポジトリに入れず、出典とライセンスの一覧（`datasets/manifest.csv`）だけを管理しています。

### 見た指標

- **SDR**：正解にどれだけ近いか。この記事で「◯ dB」と書いたら、41 クリップの平均 SDR です。
- **SIR / SAR**：SIR は他の楽器が混ざっていない度合い、SAR は処理によるノイズや歪みが少ない度合いです。
- **Retention（保持率）**：ギター本来の音をどれだけ残せたか。
- **Leakage（漏れ）**：他楽器がどれだけ混ざったか。

ほかに、「新しい候補が今のチャンピオンに勝ったら入れ替える」という Champion / Challenger 方式で、実験の記録を残し続けました。

参考までに、正解を知っている理想的なマスクを使った場合の上限は **10.70 dB** でした。

## 3. 公開モデルをそのまま試す

最初に、公開されている分離モデルを単体で評価しました。

| モデル | SDR | ひとこと |
|---|---|---|
| HTDemucs 6 stems | 2.58 dB | ギター専用ではない |
| HTDemucs 6 stems（ギター向けファインチューン版） | 3.07 dB | バランス型 |
| BS-RoFormer "SW"（6 stems のギター出力） | 3.12 dB | ギター全般には強い |
| MVSep Mega-53 のアコギ専用ヘッド | **3.13 dB** | 漏れは少ないが、ギターを大きく削る（保持率 0.33） |

どれも 3 dB 前後で横並びでした。ただ、**得意な曲がモデルごとに違う**ことがクリップ単位の結果から分かりました。これが次の一手につながります。

ちなみに、「X-LANCE のギター用モデル」として公開されていたものは、重みを比べると SW のギター部分と**完全に同一のバイト列**でした。名前が違っても中身が同じことがあるので、比較の前に重みのハッシュを確かめる価値があります。

## 4. 効いたこと

### 4-1. 系統の違うモデルを平均する（3.13 → 4.16 dB）

HTDemucs（波形＋スペクトログラムのハイブリッド）と、Mega-53 のアコギ専用ヘッド（BS-RoFormer 系）の出力を、波形のまま単純に平均しました。これだけで **4.16 dB** になりました。

- 2つのモデルは失敗するクリップが違うので、平均すると互いの失敗を打ち消し合います。
- 単体では 3.13 dB だった Mega のアコギ専用ヘッドは、「エレキやほかの楽器を拾わない」という性質のおかげで、アンサンブルの一員として最も役に立ちました。

似た発想で、「SW のギター出力から、Mega が推定したエレキギターを引き算する」方法も効きました（3.12 → 4.20 dB）。

### 4-2. 推論時の「区切りの長さ」を変える（4.16 → 5.79 dB）：一番効いた一手

分離モデルは、長い曲を一定の長さ（チャンク）に区切って処理します。このチャンク長は普段あまり意識しないパラメータですが、ここが**最大の改善ポイント**でした。

- Mega-53 の既定のチャンク長は 20 秒です。
- これを 4 秒まで短くすると、アンサンブル全体で **+1.6 dB** 上がりました。

| Mega のチャンク長 | SDR（HTDemucs は既定の 7.8 秒） |
|---|---|
| 20 秒（既定） | 4.16 dB |
| 8 秒 | 5.08 dB |
| 6 秒 | 5.58 dB |
| **4 秒** | **5.79 dB** |

短くするほど素直に良くなりました。一方、HTDemucs は学習時の長さ（7.8 秒）を超えるチャンクではそもそも動かず、7.8 秒より短くすると少し悪くなりました。つまり**最適なチャンク長はモデルごとに違う**ので、まとめて1つの値にせず、モデルごとに設定するのが正解でした。

この効果は偶然見つかりました。後述するリファイナーの学習データを 6 秒チャンクで作っていたところ、推論も 6 秒にそろえたら急に数値が上がったのがきっかけです。そこから「リファイナーの効果なのか、チャンク長の効果なのか」を切り分ける対照実験を組み、チャンク長そのものが効いていると分かりました。

### 4-3. アンサンブルの後ろに小さなネットワークを置く（→ 7.62 dB）

最後の一押しは、各モデルの出力を入力にして仕上げを行う、小さな学習済みネットワーク（ここでは「リファイナー」と呼びます）です。

```
元の曲 ─┬─ SW（ギター）──→ Mega で「エレキ」を推定して引く ─┐
        ├─ HTDemucs（ギター）───────────────────────────────┼→ 平均 → リファイナー → アコギ
        ├─ Mega-53（アコギ / ギター）─────────────────────────┤        ↑
        └─ SW・Mega の「他の楽器」推定（ボーカル、ピアノ、   ─┴────────┘
           ベース、ドラム、バイオリン、木管、エレキ）            （判断材料として入力）
```

仕組みは次のとおりです。

- **出発点はアンサンブルの平均**：リファイナーは平均した結果を受け取り、スペクトログラムの時間・周波数ごとに「この部分を何倍にするか（0〜2倍）」だけを学習します。
- **学習前は何もしない**：最終層をゼロで初期化しているので、学習前はアンサンブルの平均をそのまま出します。学習しても、元の平均より悪くなりにくい設計です。
- **他の楽器の推定も入力する**：「ここはバイオリンっぽい」「ここはエレキっぽい」という手がかりとして、他楽器の推定も渡します。
- **小さい**：パラメータ数は約 7 万です。学習自体は CPU でも 45 分ほどで終わります（時間がかかるのは、入力となる各モデルの出力を用意するほうです）。
- **学習データは検証セットと別**：6 秒のクリップ 168 本で学習し、検証セットの曲は一切使っていません。苦手なクリップを重点的に学習させる、ハードサンプル・マイニングも入れました。

このリファイナーを段階的に改良した結果が次の表です。

| 版 | 変更点 | SDR |
|---|---|---|
| r3 | 2 モデルの平均に適用 | 4.68 dB |
| r3 | 推論時のチャンク長を学習時（6 秒）にそろえた | 6.50 dB |
| r4 | 入力に「SW − エレキ」を加えて 3 モデル平均に | 6.90 dB |
| **r5** | **チャンク長をモデルごとに最適化し、学習・推論の両方でそろえた** | **7.62 dB** |

特に大事だったのは、**学習時と推論時で入力の作り方を完全にそろえる**ことです。r3 では、そろえただけでリファイナー自身の上積みが +0.53 dB から +1.03 dB へ、ほぼ倍になりました。当たり前に聞こえますが、チャンク長のような推論設定の違いも「入力の分布の違い」になります。

## 5. 効かなかったこと

効かなかったことも同じくらい参考になるので、記録しておきます。

- **邪魔な楽器を先に消してからギターを取り出す**（カスケード方式）：3通り試して、どれも SW 単体（3.12 dB）と同等かそれ以下でした。
  - ギター抽出後にバイオリン・クラリネットの推定を引く：3.12 dB（変化なし）
  - 先に弦楽器と管楽器を消してからギターを抽出：2.92 dB
  - 4 段のカスケード：10 クリップの時点で −0.42 dB だったので打ち切り

  段を重ねるたびに、ギターも少しずつ削られていきます。
- **アンサンブルの重み調整**：35:65 から 65:35 まで試しましたが、結局は等分が一番でした。
- **Wiener フィルタなどの後処理**：「漏れを減らす代わりにギターも削る」というトレードオフの線上を動くだけで、全体の SDR は上がりませんでした。
- **マスクを予測するタイプのリファイナー**（r1 / r2）：「消す」ことは学習しても、「戻す」ことができませんでした。倍率（ゲイン）を予測する方式に変えて、初めて効果が出ました。
- **周波数ごとに最適な重みを学習データから求める**：学習データでは良くても、検証セットでは −0.35 dB と悪化しました。

## 6. 最終結果

| 構成 | SDR | SIR / SAR | 保持率 |
|---|---|---|---|
| 単体モデルのベスト（Mega-53 アコギ専用ヘッド） | 3.13 dB | 14.8 / 1.2 | 0.33 |
| HTDemucs + Mega の平均 | 4.16 dB | 8.4 / 6.6 | 0.43 |
| 同じ構成で、チャンク長を最適化 | 5.79 dB | 9.9 / 8.9 | 0.61 |
| 3 モデル平均 + リファイナー r4 | 6.90 dB | 11.6 / 9.3 | 0.62 |
| **最終版（r5）** | **7.62 dB** | **12.5 / 9.5** | **0.69** |

最終版では、**漏れが減り（SIR が上昇）、しかもギターの保持率も上がり**ました。最初に決めた優先順位のとおり、「漏れを減らしつつ、ギターを削らない」方向に進めた形です。実録音で 4.89 dB、合成シナリオで 9.97 dB で、41 クリップ中 32 クリップで r4 を上回りました。

### 圧縮音源への強さ

対象曲は AAC 圧縮なので、検証セットの実録音 19 クリップを AAC 128 kbps に変換して評価し直しました。

- SDR は −0.28 dB（わずかに低下）
- 漏れは 1.3 dB 増加
- ギターの保持率は変わらず

圧縮によるダメージは主に「漏れの増加」として現れました。対象曲でも、検証の数値より少し漏れが多いと考えるのが妥当です。

### まだ苦手なこと

- **アコギと同じ音域で鳴るエレキ**：一番の弱点です。クリーンやクランチの音色だと、ギターとして残ってしまいます。
- **他の楽器に深く埋もれたギター**：伴奏と一緒にギターも削られます。
- 対象曲では、バイオリンやクラリネットが音程をなめらかに動かす箇所で、音が小さく残ることがあります。

## 7. CPU 4 コアで 45 回の実験を回すための工夫

GPU なしの環境で進めたので、計算量の工夫が欠かせませんでした。

- **bf16 で推論**：fp32 の約 1.5 倍速く、結果の差は −40 dB 程度とほぼ無視できます。
- **重みの共通部分をまとめる**：Mega-53 は楽器ごとにチェックポイントが分かれていますが、共通部分（トランク）はすべて同一でした。まとめて読み込めば、1 回の計算で 8 楽器分の推定が得られます。
- **分離結果を内容ハッシュでキャッシュ**：同じモデル・同じ設定・同じ入力なら再計算しません。途中で止まっても、終わったところから再開できます。

### ハマったところ

- **キャッシュが一度だけ外れる不具合**：キャッシュのキーは入力音声のハッシュです。初回の計算では、後段のモデルに「計算直後の float32 配列」が渡っていました。一方、2 回目以降は「FLAC に保存して読み戻した配列」が渡ります。値がわずかに違うのでハッシュも変わり、カスケードの後段が毎回一度だけ再計算されていました。初回から「読み戻した値」を渡すように直し、回帰テストを追加しました。
- **クラウド環境の再起動**：長時間ジョブの途中でコンテナが再起動したり、ディスクが満杯になったりして、何度かやり直しました。キャッシュのおかげで、失ったのは計算途中のクリップだけで済みました。

## 8. 学び

1. **物差しを先に作る**：正解付きの検証セットがあったので、「なんとなく良さそう」ではなく数字で判断できました。今回一番効いたチャンク長の発見も、この物差しがなければ気づけませんでした。
2. **推論設定は立派なハイパーパラメータ**：チャンク長のような「既定値のままにしがちな値」だけで、モデルを 1 つ足す以上の差がつきました。しかも最適値はモデルごとに違います。
3. **学習と推論の条件をそろえる**：後段ネットワークの効果は、入力の作り方を学習時とそろえるだけで倍になりました。
4. **小さく足す**：大きなモデルを学習し直す前に、既存モデルの平均と、それを微調整する小さなネットワークで、ここまで伸ばせました。
5. **効かなかったことも記録する**：カスケード方式が効かないと分かったことで、以降の時間を有望な方向に集中できました。

## 9. 動かしてみる

```bash
uv sync --extra cpu
uv run --no-sync python -m acoustic_separator --input "<音声ファイルまたはURL>" --quality max
```

- `--quality max` が最終版のパイプラインです。CPU 4 コアで、2 分の曲に 1〜1.5 時間ほどかかります（GPU ならずっと速くなります）。
- 速さを優先するなら、`--quality standard`（単体モデルのベスト、3.13 dB）か `--quality fast`（HTDemucs、3.07 dB、1 曲 50 秒ほど）も選べます。

実験の全記録は `docs/experiments.md`、最終レポートは `reports/final_report.md` にあります。
